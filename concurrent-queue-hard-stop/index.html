QA 에이전트 동시 실행 큐와 Graviton 마이그레이션

26년 04월 05일
  • #journal

DAG 스케줄러를 만들고 나니 다음 문제가 눈에 보이기 시작했다.

스케줄러가 실행 가능한 케이스를 식별하면, 그걸 실제로 어떻게 실행할 거냐는 문제다.

한 번에 다 실행하면 브라우저가 몇 개든 뜰 수 있고, 서버 메모리가 터진다.

순서를 정하는 것과 실제로 실행하는 건 다른 레이어의 문제다.

동시 실행 큐

실행 큐를 만들었다.

스케줄러가 “이 케이스들은 지금 실행 가능하다”라고 판정하면, 큐에 넣는다.

그리고 가용한 lane 수만큼만 큐에서 꺼내서 실행한다.

lane이 3개면 동시에 3개 케이스만 실행되고, 나머지는 큐에서 대기한다.

하나가 끝나면 다음 것이 큐에서 빠져나온다.

이 구조가 단순해 보이지만 구현할 때 신경 쓸 게 많았다.

큐에 넣는 시점과 lane에서 빼는 시점이 다르니까, 중간에 상태가 바뀔 수 있다.

예를 들어 큐에 있는 동안 선행 케이스가 실패해서 이 케이스가 blocked 되어야 할 수도 있다.

그러면 큐에서 꺼내기 전에 상태를 다시 확인해야 한다.

hard stop

실행 중인 케이스가 응답 없이 멈추는 경우가 있었다.

LLM이 응답하지 않거나, 브라우저가 페이지 로딩에서 무한 대기에 빠지거나.

이런 케이스를 방치하면 전체 실행이 끝나지 않는다.

하나가 멈추면 뒤에 있는 케이스들이 전부 대기 상태가 된다.

각 케이스에 타임아웃을 설정하고, 시간이 초과되면 강제로 종료하는 hard stop 기능을 구현했다.

케이스마다 기본 15분 타임아웃을 걸었다.

15분이 지나면 실행 에이전트를 강제 종료하고, 브라우저 세션도 정리한다.

좀비 프로세스가 남지 않게 브라우저 정리까지 같이 처리한다.

hard stop이 실행되면 해당 케이스는 failed로 처리된다.

hard stop은 가혹해 보이지만 없으면 안 된다. 하나의 멈춘 케이스가 전체 실행을 인질로 잡기 때문이다.

Graviton 마이그레이션

Alpha 환경을 Graviton 인스턴스(t4g.xlarge)로 마이그레이션했다.

Graviton은 ARM 기반 프로세서라서 x86 대비 가성비가 좋다.

같은 가격으로 더 많은 코어를 쓸 수 있다.

문제는 ARM64 아키텍처라서 일부 npm 패키지가 호환되지 않는다는 거다.

native addon을 쓰는 패키지들은 ARM용 바이너리가 없으면 빌드가 실패한다.

호환되는 버전으로 올리거나 대체 패키지를 찾아서 하나씩 해결했다.

특히 이미지 처리와 브라우저 자동화 쪽에서 ARM 호환성 문제가 많았다.

qa-sheet-writer 판단 기준

qa-sheet-writer의 skipAgentTest 판단 기준을 정리했다.

에이전트가 자동화할 필요가 없는 케이스를 명확히 구분하는 기준이다.

예를 들어 “페이지가 열리는지 확인” 같은 단순 검증은 에이전트 없이도 할 수 있다.

이런 케이스를 에이전트가 판단해서 건너뛰도록 기준을 정의했다.

메모 작성 지침도 개선했다.

PM이 결과를 읽을 때 어떤 정보가 필요한지 기준을 잡았다.

실패한 케이스에 “왜 실패했는지”, “재현 방법”, “예상 동작” 세 가지가 들어가도록 지침을 정했다.

마무리

동시 실행 큐와 hard stop으로 실행 안정성이 크게 올라갔다.

이제 케이스가 멈춰도 전체 실행이 끝나지 않는 일이 없다.

Graviton 마이그레이션으로 인프라 비용도 줄었다.
