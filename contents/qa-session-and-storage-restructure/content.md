Slack 결과 링크가 불일치하는 문제가 있었다.

같은 테스트 결과인데 링크를 타고 들어가면 엉뚱한 페이지가 나오거나, 스레드 제목이 테스트 대상 시트 이름과 맞지 않았다.

그리고 QA 에이전트가 CLI 기반으로 실행되다 보니 세션 상태가 매 실행마다 초기화되는 것도 문제였다.

오늘은 이 두 가지를 잡았다.

## Slack 스레드와 링크 일관성

테스트 결과 페이지 링크가 실행마다 다른 형식으로 생성되고 있었다.

링크 생성 로직을 하나로 통일했다.

그리고 Slack 스레드 제목에 시트 이름을 노출시켰다.

기존에는 "QA 실행 결과" 같은 제목이 달려서 여러 실행 결과를 구분하기 어려웠다.

이제는 "QA 실행 결과 — 회원가입 플로우 시트"처럼 어떤 시트를 검증했는지 스레드 제목만 봐도 안다.

Slack에서 과거 실행 결과를 찾을 때 검색으로 바로 걸린다.

## opencode server session 전환

그 전까지 QA 에이전트는 CLI를 일회성으로 실행하는 구조였다.

실행할 때마다 새 프로세스를 띄우고 끝나면 프로세스가 죽으면서 세션 상태가 사라진다.

이게 문제가 된 건 planning과 실행을 분리하려고 할 때였다.

planning 결과를 실행 단계로 넘기려면 세션이 살아 있어야 하는데, CLI가 죽어버리니까 상태를 전달할 방법이 없었다.

그래서 opencode server 기반 세션 구조로 전환했다.

planning 전용 세션 1개가 상시 떠 있고, 실행 lane마다 별도 세션이 할당된다.

planning 세션이 실행 계획을 수립하면, 각 lane 세션이 그 계획을 받아서 병렬로 실행한다.

세션이 살아 있으니까 실행 중에 planning 세션에 추가 질의를 하거나, 실행 결과를 다시 planning에 피드백하는 것도 가능해진다.

> CLI 기반에서 서버 기반으로 바꾸니까 디버깅도 편해졌다. 세션이 살아 있으니까 실행 중에 상태를 inspect할 수 있다.

## 영구 저장소 분리

fixture knowledge, 에이전트 스킬, planning 캐시가 전부 코드 저장소 안에 있었다.

이게 문제인 이유는 두 가지다.

첫째, 코드 저장소는 버전 관리 대상이라 fixture나 캐시 같은 런타임 데이터가 들어가면 diff가 지저분해진다.

둘째, 여러 에이전트가 같은 데이터에 접근해야 하는데 코드 저장소 안에 있으면 경로가 에이전트별로 달라진다.

이 세 가지(fixture knowledge, 에이전트 스킬, planning 캐시)를 코드 저장소 외부의 영구 저장소로 통합했다.

이제 모든 에이전트가 같은 경로에서 fixture를 읽고 같은 경로에 스킬을 쓴다.

데이터 일관성이 잡혔다.

코드 저장소 diff도 깔끔해졌다.

## 마무리

서버 기반 세션 전환은 앞으로 멀티 에이전트 구조로 넘어가기 위한 기반 작업이었다.

세션이 분리되어 있으니까 각 에이전트가 독립적으로 동작하면서도 필요할 때 서로 통신할 수 있다.

영구 저장소 분리도 유지보수 측면에서 이득이다.

런타임 데이터와 코드가 섞이지 않으니까 각각 관리하기 편하다.
