3단계 planning을 단일 플래너로 합치면서 메모리 문제도 같이 해결한 날이었다.

## 단일 플래너 통합

이틀 전에 3-Phase Planning Pipeline을 만들었다.

골격 → 그룹별 상세 → 조립, 3단계로 나눠서 planning 멈춤을 해결했다.

그런데 3단계 구조의 복잡도가 예상보다 컸다.

Phase 간 데이터 전달, 에러 처리, 재시도 로직이 각각 필요했다.

코드가 복잡해지니까 디버깅도 어려워졌다.

그래서 다시 단일 플래너로 합쳤다.

하지만 무식하게 합친 게 아니다.

컨텍스트 압축을 활용해서 단일 플래너가 한 번에 처리할 수 있도록 만들었다.

3단계 구조에서 만든 36개 파일 약 1200줄을 삭제했다.

코드가 단순해지니까 유지보수가 훨씬 편해졌다.

## qa-vision 서브에이전트

플래너에서 시각 판단을 분리했다.

스크린샷을 보고 "이 페이지가 의도한 대로 렌더링되었는가"를 판단하는 건 시각적 추론이 필요하다.

이걸 플래너가 하려면 멀티모달 모델을 써야 하는데, 비싸고 느리다.

qa-vision 서브에이전트가 시각 판단만 전담하도록 분리했다.

플래너는 텍스트 기반 가벼운 모델로 planning에만 집중한다.

## Docker 메모리 고갈

Alpha 환경에서 Docker 메모리가 자꾸 고갈됐다.

호스트 메모리 8GB 중 QA 에이전트가 5GB 이상을 사용하고 있었다.

원인을 추적해보니 Chromium 4인스턴스가 동시에 실행되고 있었다.

lane별로 독립적인 브라우저를 띄우니까 4개가 동시에 돌아간 거다.

Chromium 하나당 약 1~2GB를 먹으니까 4개면 4~8GB다.

8GB 서버에서는 당연히 터진다.

Chromium 환경변수를 런타임에 통합하고 Dockerfile의 중복 설정을 정리했다.

메모리 사용량이 눈에 띄게 줄었다.

### 세션 ID 추출 실패

세션 ID 추출이 간헐적으로 실패하는 문제도 해결했다.

원인이 세 가지였다.

LLM이 idle 상태를 오판하는 경우, sharp 라이브러리가 누락된 경우, 동시 요청 과부하.

세 가지 원인을 각각 수정했다.

## 스크린샷 의무화

각 케이스 실행 결과에 스크린샷을 의무화했다.

스크린샷이 없으면 결과 리포트에 증거가 없다.

실행 흐름에 스크린샷 생성을 체크리스트 항목으로 넣었다.

## 마무리

단일 플래너로 합치면서 코드 복잡도를 크게 낮췄다.

메모리 고갈 해결은 Alpha 환경 안정성에 직결되는 수정이었다.
