## 의존성 판정이 자꾸 흔들리더라

QA 에이전트에서 테스트 케이스 사이의 의존성을 판정하는 건 계속 골치였다.

앞선 케이스가 실패하면 뒤따르는 케이스를 어떻게 처리할지, 어디까지 묶어서 막을지를 planner가 매번 판단해야 한다.

그런데 판정 기준이 모호하니까 같은 상황에서 결과가 자꾸 달라졌다.

로그인이 깨졌는데도 강의 수강 케이스를 그냥 진행하거나, 반대로 사소한 경고에도 하위 케이스를 전부 막아버리는 식이었다.

패스율이 들쑥날쑥하니 디버깅도 어렵고 실패 원인이 의존성 판정인지 실제 결함인지 구분이 안 됐다.

그래서 판정 로직 자체를 갈아엎기로 했다.

## Q-UI와 Q-RUNTIME, 질문 두 개로 쪼갰다

핵심은 planner가 던지는 질문을 두 가지로 좁힌 것이다.

하나는 Q-UI다.

선행 케이스가 실패했을 때 UI 상태가 더 진행할 수 없을 정도로 망가졌는지를 묻는다.

예를 들어 로그인이 안 됐으면 화면 자체가 진입 불가능한 상태고 이건 Q-UI 실패로 본다.

다른 하나는 Q-RUNTIME이다.

런타임 데이터, 세션, fixture knowledge 같은 쪽의 상태가 하위 케이스를 돌릴 수 있는지를 묻는다.

토큰이 만료됐거나 세션이 꼬였으면 Q-RUNTIME 실패로 처리한다.

이 두 질문을 명시적으로 가르니 이전엔 한 덩어리로 뭉뚱그려지던 실패 원인이 UI 쪽인지 런타임 쪽인지로 깔끔하게 나뉘었다.

## cascade block을 다시 살렸다

재설계하면서 cascade block 동작도 같이 복원했다.

선행 케이스가 Q-UI나 Q-RUNTIME에서 실패하면 그 케이스에 의존하는 하위 케이스는 자동으로 blocked 처리된다.

이건 이전에 한 번 뒀던 `hardBlockDownstream` 흐름과 맥락이 같다.

다만 이번엔 블록 조건을 두 질문의 결과로 명시하니까 왜 하위 케이스가 막혔는지를 코드로 설명할 수 있게 됐다.

"UI가 망가졌으니까 막았다" 혹은 "런타임이 안 돼서 막았다"가 로그에 남는다.

예전엔 "의존성 실패" 한 줄로 끝나니까 원인을 파묻어둔 거나 마찬가지였다.

## 패스율 73.3%까지 올랐다

이렇게 바꾸고 나서 30개 케이스 기준으로 검증을 돌렸다.

통과한 케이스가 22개, 패스율로 치면 73.3%다.

숫자만 놓고 보면 그럭저럭이지만 중요한 건 패턴이 안정된 것이다.

같은 시트를 여러 번 돌려도 패스율 흔들림이 줄었고 blocked 케이스의 사유가 명확하게 분류됐다.

이전엔 무작위로 깨지는 느낌이었는데 이제는 실패 원인별로 그룹을 묶어서 볼 수 있어서 회귀 분석이 훨씬 편해졌다.

## 남는 고민

두 질문 모델이 모든 케이스를 커버하진 않는다.

가끔 UI와 런타임 경계가 흐릿한 경우가 있는데 그때는 planner가 어느 쪽으로 분류할지 판단이 또 흔들린다.

경계 케이스를 어떻게 다룰지는 다음 작업으로 남겨뒀다.

그래도 의존성 판정을 "왜 막았는지 설명 가능한 상태"로 만든 건 큰 수확이다.

설명 가능한 실패가 쌓여야 회귀 테스트가 의미를 가진다고 생각한다.
