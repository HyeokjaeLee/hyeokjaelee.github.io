어제 agent-browser 기반으로 전환했으니, 오늘은 이 구조를 실제로 검증하고 실행 흐름을 개선했다.

하루 동안 다섯 가지를 손봤다.

## agent-browser 2차 검증

어제 agent-browser 전환 후 타입체크, 테스트, 린트, 스모크를 통과했다.

오늘은 실제 케이스를 돌리면서 agent-browser 스킬 사용을 2차로 검증했다.

마스터가 브라우저를 준비하고 실행 에이전트가 가져다 쓰는 흐름이 정상 동작하는지 확인했다.

브라우저 격리도 의도대로 동작했다.

lane마다 독립된 브라우저 세션을 쓰니까 한 lane에서 페이지를 이동해도 다른 lane에 영향을 주지 않는다.

## thinking 이벤트 로깅

LLM의 thinking 이벤트를 로깅하도록 추가했다.

LLM이 추론하는 과정을 로그로 남기면, 나중에 "왜 이 케이스를 실패로 판정했지?"라고 물었을 때 답을 찾을 수 있다.

thinking 이벤트 없이 결과만 보면 LLM이 왜 그런 판정을 내렸는지 알 수 없다.

추론 과정을 로그로 남기니까 디버깅이 훨씬 수월해졌다.

## executionDraft 필드 도입

플래너가 단계별 실행 초본을 작성할 수 있도록 executionDraft 필드를 도입했다.

이전에는 플래너가 실행 계획만 수립하고, 실행 에이전트가 계획을 받아서 각 단계를 즉석에서 결정했다.

executionDraft는 플래너가 각 단계에서 무엇을 할지 초안을 미리 적어두는 것이다.

실행 에이전트는 이 초안을 기반으로 실제 실행을 수행한다.

초안이 있으니까 실행 에이전트가 매 단계마다 처음부터 생각하지 않아도 된다.

플래너의 의도가 실행 에이전트에게 더 정확하게 전달된다.

## fixture knowledge 정상화

fixtures.sqlite가 정상적으로 동작하지 않는 문제를 해결했다.

실행 에이전트가 fixture를 조회할 때 경로가 잘못되어 있어서, 이전 실행에서 학습한 지식을 가져오지 못하고 있었다.

매번 새로 학습하니까 실행 시간이 길어지고 비용이 늘었다.

조회 흐름을 개선해서 fixture가 정상적으로 로드되도록 수정했다.

> fixture knowledge가 동작하면 같은 페이지를 테스트할 때 이전에 찾은 셀렉터를 재사용할 수 있다. 매번 셀렉터를 새로 찾는 건 시간도 오래 걸리고 비용도 든다.

## delegation 루프 도입

qa-master에 delegation 루프를 도입했다.

이전에는 마스터가 각 에이전트를 순차적으로 호출했다.

delegation 루프는 task 기반 실행이다.

마스터가 task를 만들고, 적절한 에이전트에게 위임한다.

위임받은 에이전트가 task를 수행하고 결과를 반환하면, 마스터가 다음 task를 결정한다.

이 루프 구조가 들어오니까 실행 흐름이 유연해졌다.

중간에 실패하면 마스터가 다음 task를 조정할 수 있다.

순차 호출에서는 이런 유연성이 없었다.

## 마무리

하루에 다섯 가지를 손봤더니 진도가 빨랐다.

delegation 루프가 들어오니까 실행 구조가 한층 더 단단해진 느낌이다.
