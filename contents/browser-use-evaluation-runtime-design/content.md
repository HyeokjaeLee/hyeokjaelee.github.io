QA 에이전트의 브라우저 자동화 구조에 대한 고민이 깊어지는 날이었다.

지금은 Playwright MCP로 브라우저를 조작하고 있다.

세션도 분리했고 lane도 병렬로 돌리고 있는데, 런타임 복잡도가 점점 커지고 있었다.

## 복잡도의 원인

브라우저 관리가 여전히 병목이었다.

lane마다 브라우저를 띄우고, 정리하고, 세션을 유지하는 코드가 각 lane마다 중복되어 있었다.

그리고 브라우저 셀렉터 관리가 피곤하다.

매 페이지마다 `data-testid`나 CSS 셀렉터를 찾아야 한다.

페이지 구조가 바뀌면 셀렉터도 같이 바꿔야 한다.

## browser-use 검토

browser-use라는 도구를 검토했다.

LLM이 자연어로 브라우저를 조작할 수 있게 해주는 도구다.

"로그인 버튼을 찾아서 클릭해"라고 지시하면 알아서 요소를 찾고 클릭한다.

매력적인 점은 셀렉터를 직접 관리하지 않아도 된다는 거다.

LLM이 페이지를 보고 적절한 요소를 찾으니까, 페이지 구조가 바뀌어도 대응할 수 있다.

### 도입하지 않기로 한 이유

그대로 도입하기엔 우려가 있었다.

browser-use는 LLM이 매 액션마다 추론을 해야 하니까 실행 속도가 느려진다.

셀렉터 찾는 속도보다 LLM 추론 속도가 훨씬 느리다.

QA 실행은 케이스가 많으니까 속도가 중요하다.

그리고 LLM이 페이지를 잘못 해석하면 엉뚱한 요소를 클릭할 수 있다.

"로그인"이라는 텍스트가 페이지에 두 개 있으면 어느 쪽을 클릭할지 보장할 수 없다.

QA 에이전트는 정확성이 중요하니까 추론 기반보다 확정적 실행이 낫다고 판단했다.

## 오케스트레이션 계층 분리

browser-use를 메인 브라우저 도구로 쓰지 않기로 했으니, 기존 구조를 어떻게 개선할지가 관건이었다.

OpenCode를 오케스트레이션 계층으로 유지하면서 런타임 복잡도를 낮추는 방향을 잡았다.

핵심은 역할 분리다.

브라우저를 띄우고 관리하는 건 마스터 에이전트만 한다.

실행 에이전트는 마스터가 준비해 둔 브라우저를 가져다 쓰기만 한다.

브라우저 소유권이 명확해지니까 세션 충돌이 사라진다.

이 구조가 잡히면 브라우저 관리 코드가 한 곳에 집중되니까 복잡도가 크게 줄어든다.

> 오케스트레이션 계층과 실행 계층을 분리하면 디버깅도 편해진다. 문제가 생기면 마스터인지 실행 에이전트인지부터 확인하면 된다.

## 마무리

browser-use를 도입하지 않기로 한 건 아깝긴 하지만, 확정적 실행이 QA에 더 맞는 선택이었다.

대신 런타임 구조를 단순화하는 방향으로 설계를 잡았다.

내일은 이 설계를 실제로 구현해서 돌려볼 예정이다.
