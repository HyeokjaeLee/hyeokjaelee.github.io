## 임베딩 분류기의 한계

ClawMux에서 요청 복잡도에 따라 LIGHT/MEDIUM/HEAVY 3티어로 라우팅하는 분류기를 만들어 쓰고 있었다.
초기엔 키워드 스코어러였다가, 이내 `paraphrase-multilingual-MiniLM-L12-v2` 로컬 임베딩 모델 기반 nearest-centroid 분류기로 바꿨다.
커밋 하나에 파일 16개, `+1,291/-967` 정도의 규모로 갈아치운 전환이었다.

근데 쓰다 보니 한계가 보였다.
경량 사전학습 모델이다 보니 내 서비스 도메인에 딱 맞는 분류 기준을 학습시키기가 애매했고, 단문 쿼리를 억지로 LIGHT로 보내는 `isLikelyLight()` 같은 휴리스틱이 자꾸 늘어났다.
휴리스틱이 늘어난다는 건 분류기 본연의 판단을 코드로 덮어쓰고 있다는 뜻이다.
결국 임베딩 모델을 더 탐색해보다가, 아예 LLM 자체를 분류기로 쓰는 방향으로 마음을 정했다.

## LLM 분류기로 전환

저렴한 LLM을 분류기로 쓰기로 했다.
핵심은 비용 최소화다.
reasoning을 끄고, `max_tokens=1`로 고정했다.
응답은 `L`, `M`, `H` 한 글자만 돌려받도록 강제한다.
한 글자면 충분하다.

이전 임베딩 분류기엔 컨텍스트가 부족할 때를 대비한 `Q` 옵션이 있었다.
근데 LLM 분류기는 전체 messages를 받아서 판단하니, 컨텍스트 부족 케이스 자체가 사라졌다.
그래서 Q 옵션을 과감히 제거했다.
대신 시스템 프롬프트에 "마지막 메시지와 관련 주제로 판단하라"는 지시를 넣었다.

형식 오류가 돌아오면 에러 피드백과 함께 최대 2회 재시도한다.
그래도 실패하면 503 에러를 그대로 전달한다.
조용한 폴백은 만들지 않았다.
분류가 안 되면 차라리 실패가 낫다고 생각한다.

## reasoning 비활성화

분류기 LLM이 reasoning에 토큰을 소모하면 `max_tokens=1` 정책이 의미가 없어진다.
그래서 `reasoning-disable.ts` 모듈을 만들었다.
API 포맷별로 reasoning을 끄는 파라미터가 다 달라서, 6개 포맷을 각각 처리했다.

이게 생각보다 귀찮은 작업이었다.
포맷마다 필드 이름도 다르고, 어떤 건 아예 지원을 안 하기도 한다.
다행히 분류기 한 곳에서만 쓰니 모듈 하나로 묶어두니 깔끔했다.

## 동적 컨텍스트 창

분류기에 전체 messages를 넘기다 보니, 컨텍스트 창 초과를 처리해야 했다.
`trimToContextWindow`로 초과하면 오래된 메시지부터 잘라낸다.
여기서 문제가 생겼다.
컨텍스트 창 크기를 어디서 읽어올 거냐는 거다.

`clawmux.json > 외부 프로바이더 설정 > 내장 카탈로그 > 200K 기본값` 순서로 해석하도록 만들었다.
사용자가 명시한 값이 최우선이고, 설정이 없으면 카탈로그 기본값, 그것도 없으면 200K로 떨어진다.
그리고 provider/model 형식을 강제했다.
모델 ID에 프로바이더명을 반드시 붙여야 한다.
이걸 안 하면 어느 프로바이더의 모델인지 모호해져서 컨텍스트 창을 제대로 못 읽어온다.

## baseUrl 중복 문제

전환 과정에서 버그 하나를 잡았다.
baseUrl에 이미 버전 경로(`/v1`)가 포함된 프로바이더가 있었는데, 어댑터가 거기에 또 `/v1`을 붙이고 있었다.
경로가 중복되니 API 호출이 전부 실패했다.
baseUrl 정규화 로직을 넣어서 해결했다.

## 남은 과제

`bun run typecheck`는 0 에러로 통과했다.
근데 라이브 테스트에서 변수가 생겼다.
한 프로바이더는 잔액 부족(429)이 떴고, 다른 하나는 `max_tokens=1`에서 빈 content를 돌려줬다.
`max_tokens=1`이라 응답이 잘리는 케이스인 것 같다.
프로바이더 호환성을 좀 더 조사해야 한다.
분류기 전환 자체는 끝났지만, 실제로 여러 프로바이더에서 안정적으로 돌아가려면 케이스가 좀 더 필요하다.

> 한 글자 응답에 reasoning 끄고 컨텍스트 창 동적 해석까지 — 분류기 하나에 신경 쓸 게 의외로 많다.
