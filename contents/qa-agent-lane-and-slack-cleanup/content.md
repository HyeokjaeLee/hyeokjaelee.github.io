QA 에이전트의 실행 로그를 하나로 합치고, Slack 메시지 정책을 단순화했다.

기존에는 lane별 실행 로그가 파일마다 흩어져 있었다.
한 번 실행에 결과가 3~5개 파일로 쪼개지니, 어디서부터 읽어야 할지 매번 헤맸다.
lane 실행 로그 3개를 통합하고, Slack `/qa` 명령이 첨부하는 메시지와 파일 정책을 줄였다.

## lane 수를 동적으로 선택하기

그동안 lane 수를 고정해 두고 쓰고 있었다.
케이스가 많을 때는 lane이 부족해서 실행이 밀리고, 적을 때는 빈 lane만 돌고 있었다.

planner가 테스트케이스 특성에 맞춰 lane 수를 1에서 5 사이에서 고르도록 바꿨다.
의존성이 많이 엮인 케이스는 lane 수를 줄이고, 서로 독립적으로 돌 수 있는 케이스가 많으면 lane을 늘린다.
DAG로 의존성을 관리하고 있으니, 선행 케이스가 끝난 뒤 후행 케이스를 같은 lane에 이어 붙이는 식으로 병렬성을 최대한 쥐어짠다.

한 번의 실행에서 lane 로그가 흩어지는 문제도 같이 잡았다.
lane 수가 달라질 때마다 로그 파일이 늘어나던 걸 하나로 합쳤다.
이제는 실행이 끝나면 결과를 한 파일에서 위에서 아래로 읽으면 된다.

## Slack 메시지 정책 줄이기

QA 에이전트는 Slack 봇으로 동작한다.
`/qa` 명령을 치면 테스트가 시작되고, 끝나면 결과를 쓰레드로 올린다.

첨부가 너무 많았다.
lane별 로그 파일, 요약, 상세 결과, 에러 리포트를 각각 올리니 한 실행에 슬랙 메시지가 열 개를 훌쩍 넘겼다.
메시지를 올리는 데 시간도 걸리고, 슬랙 채널이 결과로 도배되니 다른 대화가 밀려 내려갔다.

첨부를 요약 하나와 통합 로그 하나로 줄였다.
상세 결과가 필요하면 통합 로그에서 찾으면 된다.
메시지가 줄어드니 실행 완료 알림도 빨라졌다.

## 사이드 프로젝트 검증

괴담을 수집해서 소설로 각색하는 사이드 프로젝트의 에피소드 생성이 DEV 환경에서 정상 동작하는지 확인했다.

스키마 기준으로 에피소드가 생성되는 전체 흐름을 한 번 돌려봤다.
데이터가 들어가고 나오는 시점마다 스키마와 맞는지 검증했고, 에피소드가 정상적으로 만들어지는 걸 확인했다.

따로 코드를 고친 건 없고, 검증 자체가 목적이었다.
이 검증 흐름을 자동화해 두면 다음에는 수동으로 안 돌려도 된다.

## Daily 노트 작성 규칙 정리

옵시디언에서 매일 쓰는 Daily 노트의 규칙을 스킬로 정리했다.

frontmatter에는 `date`만 남기고, 프로젝트 카테고리 헤딩부터 바로 시작한다.
기술 용어는 가능하면 쉬운 한국어로 풀어쓰고, 본문과 연관 문서 사이에 구분선을 넣는다.
wikilink는 실제 존재하는 노트만 걸도록 제한했다.

매번 노트를 쓸 때마다 어투가 섞이거나 링크가 깨지는 걸 막으려면, 규칙이 코드(스킬)로 박혀 있어야 한다.
사람이 매번 신경 쓰는 것보다 에이전트가 규칙을 적용하는 쪽이 일관성이 낫다.

정리한 규칙은 `obsidian-daily-note-writing` 스킬과 `obsidian-cli-doc-writing` 스킬에 반영했다.
앞으로 Daily 노트를 자동으로 생성할 때 이 규칙을 따른다.
