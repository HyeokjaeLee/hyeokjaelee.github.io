QA 에이전트를 만들기 시작한 지 이틀째다.

어제는 기본 파이프라인을 세우고 lane이라는 개념을 도입했다.

lane은 병렬 실행 단위다. 한 번에 여러 테스트 케이스를 돌릴 수 있는 채널이다.

오늘은 이 lane을 어떻게 운영할지, 실행 결과를 Slack에 어떻게 보낼지 정리했다.

## lane 실행 로그 통합

lane별로 실행 로그가 세 개 파일로 나뉘어 있었다.

요약 로그, 상세 결과 로그, 에러 리포트가 각각 별도 파일이었다.

누가 어떤 로그를 봐야 하는지 헷갈렸다.

세 개를 하나로 합쳤다.

하나의 로그 파일에 lane 번호, 실행 시간, 결과, 에러가 시간순으로 쌓인다.

로그를 하나씩 뒤지지 않아도 전체 흐름이 한눈에 보인다.

## lane 수 동적 선택

처음에는 lane을 3개로 고정했다.

그런데 케이스가 5개일 때와 30개일 때 필요한 lane 수가 다르다.

5개 케이스에 lane 3개면 충분하지만, 30개 케이스에 lane 3개면 실행 시간이 너무 길어진다.

반대로 케이스가 2개인데 lane 3개면 하나는 놀고 있다.

플래너가 케이스 특성에 따라 lane 수를 동적으로 선택하도록 개선했다.

플래너는 전체 케이스 수와 의존성 구조를 보고 1부터 5까지 lane 수를 결정한다.

케이스가 적으면 lane을 줄이고, 많고 의존성이 낮으면 lane을 늘린다.

## Slack 메시지 정책

Slack `/qa` 명령어로 QA를 실행하면 결과가 Slack에 온다.

기존에는 결과 메시지에 첨부 파일이 너무 많았다.

요약, 상세 결과, 스크린샷, 에러 리포트를 전부 첨부하니까 메시지가 길어져서 읽기 어려웠다.

첨부 정책을 단순화했다.

요약 메시지에 가장 중요한 정보만 담는다. 통과 수, 실패 수, 실행 시간.

상세 결과는 스레드에 넣었다. 요약 메시지에 답글로 상세 결과를 붙인다.

핵심은 "메시지를 열었을 때 바로 상태를 파악할 수 있어야 한다"는 거다.

> Slack 메시지는 가독성이 생명이다. 첨부가 많으면 사람들이 안 읽는다. 핵심만 보여주고 디테일은 접어두는 게 낫다.

## 사이드 프로젝트 DEV 검증

괴담 소설 사이드 프로젝트에서 DEV 환경 스키마로 에피소드 생성이 정상 동작하는지 검증했다.

DEV 스키마가 프로덕션과 구조가 달라서 에피소드 생성 로직을 DEV에 맞게 조정했다.

정상 동작을 확인했다.

## 옵시디언 노트 규칙

옵시디언 Daily 노트 작성 규칙을 정리했다.

매일 어떤 구조로 노트를 쓸지, 어떤 태그를 쓸지 규칙을 만들었다.

노트가 쌓이면 나중에 회고나 블로그를 쓸 때 유용하다.

## Slack 봇 Socket Mode

Slack 봇의 Socket Mode 연결 절차를 문서화했다.

Socket Mode는 Slack 앱이 HTTP 엔드포인트 없이 WebSocket으로 이벤트를 받는 방식이다.

방화벽 뒤에서도 동작하니까 개발 환경에서 쓰기 편하다.

하지만 연결 절차가 직관적이지 않아서 문서화해뒀다.

## 마무리

lane 수를 동적으로 선택하니까 케이스 수에 관계없이 적절한 실행 시간이 나온다.

Slack 메시지를 단순화하니까 결과를 빠르게 파악할 수 있다.

내일은 캐싱 정책을 손볼 예정이다.
