## 두 개를 하나로 합치게 된 이유

기존에 컨텍스트 압축을 담당하던 Context-Gateway와, 모델 라우팅을 담당하던 openclaw-router가 따로 있었다.

둘 다 OpenClaw 플러그인이었고, 각자 잘 동작했다.
문제는 둘을 같이 쓸 때 연결 지점이 애매했다.

Context-Gateway가 컨텍스트를 압축해서 넘기면, router가 그걸 받아 적절한 프로바이더로 라우팅하는 구조였는데, 중간에 포맷 변환이 두 번 일어나는 경우가 있었다.
압축은 Anthropic 포맷 기준으로 하고, 라우팅은 OpenAI 포맷으로 바꿔서 보내고, 응답은 다시 Anthropic으로 역변환하는 식이다.

플러그인 두 개를 엮어 쓰는 것 자체는 나쁘지 않은데, 이 중간 변환 로직이 양쪽에 중복되어 흩어져 있으니 유지보수가 불편했다.
그래서 두 기능을 하나의 플러그인으로 합치기로 했다.
이름은 ClawMux.

## 핵심 기능 세 가지

ClawMux가 하는 일을 한 줄로 요약하면 "OpenClaw용 LLM 프록시"다.
들어온 요청을 분류하고, 적절한 프로바이더로 보내고, 필요하면 컨텍스트를 압축한다.

구체적으로 세 가지를 구현했다.

첫째, 크로스 프로바이더 라우팅.
Anthropic 포맷으로 들어온 요청을 ZAI, OpenAI, Codex 등 다양한 프로바이더로 보낼 수 있게 했다.
6개 API 어댑터를 만들었고, 포맷 변환은 파이프라인 안에서 자동으로 처리된다.
ZAI가 OpenAI 호환 API만 제공하다 보니 Anthropic → OpenAI → Anthropic 이중 변환은 피할 수 없는 구조였다.

둘째, LLM 기반 요청 분류기.
모든 요청을 복잡도에 따라 LIGHT / MEDIUM / HEAVY 세 단계로 나눈다.
단순한 요청엔 저렴한 모델을, 복잡한 요청엔 강력한 모델을 배정하기 위해서다.
비용 최적화의 핵심은 "어디에 돈이 들어가는지" 아는 거라고 생각하는데, 분류기가 그 역할을 한다.

셋째, 컨텍스트 압축.
OpenClaw 스타일의 구조화 프롬프트로 대화를 요약한다.
대화가 길어져 compaction 요청이 오면, 백그라운드에서 미리 만들어둔 요약을 즉시 반환한다.
upstream을 안 거치니까 응답이 빠르다.

## 분류기를 키워드에서 LLM으로

초기 분류기는 키워드 기반이었다.
14차원 스코어러로 요청을 찍어서 티어를 매기는 방식이었는데, 이게 잘 안 맞았다.

한국어 요청이랑 영어 요청의 패턴이 다르고, 같은 단어라도 맥락에 따라 복잡도가 달랐다.
키워드로 잡으면 예외가 계속 생겨서 룰이 점점 더러워졌다.

그래서 과감히 키워드 스코어러를 통째로 버리고 LLM 분류기로 바꿨다.
마지막 사용자 메시지를 보고 LLM이 L / M / H / Q(맥락 부족) 한 글자로 답하는 구조다.

Q가 반환되면 이전 메시지 몇 개를 더 포함해서 재분류하고, 그래도 Q면 MEDIUM 으로 처리한다.
형식 오류가 나면 에러 피드백과 함께 재시도하고, 최대 2회까지 했을 때도 실패하면 503을 내보낸다.

LLM 분류기로 바꾸니 정확도가 확 올랐다.
한 글자만 생성하니 토큰 비용도 거의 들지 않았다.
"분류에 LLM을 쓰면 비싸지 않느냐"라고 생각했었는데, 실제로는 정반대였다.
정확한 분류 덕분에 전체 요청 비용이 오히려 줄었다.

> 이후엔 임베딩 기반 분류기로 한 번 더 바뀐다.
> 로컬 임베딩 모델(Xenova/paraphrase-multilingual-MiniLM-L12-v2, 118MB)로 nearest-centroid 분류를 하는 구조다.
> 하지만 첫 구현에서 LLM 분류기를 선택한 건, "단순한 걸 먼저 만들고 측정한다"는 접근이었다는 측면이 크다.

## 검증

ClawMux는 TypeScript 로 짜서 `tsc --noEmit` 으로 타입 에러를 잡고, bun test 로 531개 케이스를 전부 통과시켰다.
`as any`나 `@ts-ignore` 없이, 빈 catch 블록 없이, 외부 의존성 없이 만드는 걸 기준으로 삼았다.

외부 의존성을 zero 로 유지한 건 의도적이다.
프록시 서버는 장애가 나면 전체가 멈추기 때문에, 의존성 하나하나가 잠재적 장애 지점이라고 생각했다.
물론 모든 걸 직접 짜는 게 항상 정답은 아니겠지만, 이번엔 그게 합리적인 선택이었다.

## 남은 과제

초기 구현이 끝난 뒤에도 계속 손이 갔다.
스트림 응답 처리 버그, GPT-5.4 Responses API 호환성, 인증 에러, 설정 경로 통일 등등.
프록시라는 게 한 번 만들면 끝이 아니라, 프로바이더 쪽 API가 바뀔 때마다 따라가야 하는 게 더 큰 일인 것 같다.

다만 두 개의 플러그인을 하나로 합친 건, 이후 유지보수 비용을 확실히 줄여줬다.
연결 지점이 사라지니까, 중간 변환 로직을 한 곳에서만 관리해도 된다.
"작게 시작해서 측정하고, 진짜 문제가 보이면 합친다"는 흐름이 이번엔 잘 먹혔다.
