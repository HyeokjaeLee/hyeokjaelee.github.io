## 왜 실행 모델을 갈아엎었나

QA 에이전트의 실행 모델이 처음엔 단순했다.
테스트 케이스를 몇 개 그룹으로 나누고, 그룹 안에서 순차적으로, 그룹끼리는 병렬로 돌리는 구조였다.

이게 케이스가 5~10개일 땐 괜찮았다.
그런데 30~50개로 늘어나니 한계가 보였다.

가장 큰 문제는 의존성이었다.
"강의 수강" 케이스는 "로그인"이 먼저 성공해야 하고, "수료증 다운로드"는 "강의 완료"가 선행되어야 한다.
이런 의존성을 그룹 단위로만 표현하려니, 실제보다 보수적으로 실행 순서가 고정되는 경우가 생겼다.
로그인과 무관한 케이스들까지 로그인 그룹 뒤로 밀리는 식이다.

병렬성을 충분히 못 쓰니 실행 시간이 길어졌고, 실행 시간은 곧 토큰 비용이었다.
어디에 돈이 들어가는지 모르면 최적화할 수 없는데, 그룹 기반 모델에선 "왜 이 케이스가 지금 실행돼야 하는지"를 설명하기가 어려웠다.

그래서 실행 모델 자체를 DAG(Directed Acyclic Graph) 기반으로 바꾸기로 했다.

## DAG 기반 의존성 스케줄링

핵심은 테스트 케이스 간의 의존성을 간선으로 표현하고, 위상 정렬로 실행 순서를 결정하는 것이다.

케이스 A가 케이스 B의 결과에 의존하면, A → B 간선을 긋는다.
이 그래프에서 선행 케이스가 모두 끝난 케이스들은 동시에 실행할 수 있다.

여기에 Lane 이라는 개념을 넣었다.
Lane은 병렬로 실행 가능한 케이스 그룹인데, Planner가 1~5개 범위에서 상황에 맞게 동적으로 선택한다.
브라우저를 몇 개까지 동시에 띄울 수 있는지, 케이스들 사이에 자원 경합이 있는지를 보고 결정한다.

그리고 `hardBlockDownstream` 이라는 플래그를 뒀다.
선행 케이스가 실패하면 그것에 의존하는 하위 케이스들을 자동으로 blocked 처리하는 스위치다.
"로그인 실패했는데 강의 수강을 시도할 필요는 없다"는 논리를 시스템에 박아넣은 셈이다.

## 의존성을 단순화하는 게 더 어려웠다

재밌는 건, DAG로 넘어가면서 오히려 의존성 종류를 줄였다는 거다.

처음엔 의존성 유형이 여러 개 있었다.
`prerequisites`(반드시 선행), `helpfulBefore`(순서상 이득이지만 필수 아님) 같은 식으로.

소프트 의존성을 넣은 이유는 단순했다.
실행 순서를 더 똑똑하게 최적화하면 좋지 않겠느냐는 생각이었다.

하지만 실제로 돌려보니 이 "좋아 보이는" 기능이 문제였다.
의존성 그래프가 복잡해지니 디버깅이 어려워졌다.
"이 케이스가 왜 지금 실행되는지"를 설명하려 그래프를 더듬어야 했고, 소프트 의존성이 실제로 성능에 얼마나 기여하는지도 불분명했다.

결국 `prerequisites` 기반 하드 의존성만 남기고 전부 제거했다.
그러니 그래프가 훨씬 깔끔해졌고, 실행 시간 예측도 가능해졌다.

복잡함을 더하면 더 똑똑해질 거라는 가정이 틀렸다.
오히려 복잡함을 빼는 쪽이 더 나은 설계가 되는 경우가 있었다.

## 구현 규모와 검증

이번 재구현에서 17개 파일을 수정했다.
위상 정렬 기반 병렬 실행 스케줄러를 새로 짜고, Planner가 의존성 그래프를 구성하도록 바꾸고, Executor가 Lane 단위로 병렬 실행되도록 고쳤다.

중간에 중요한 버그가 4개 나왔다.
의존성 사이클이 생기는 케이스, Lane 경합이 제대로 안 풀리는 케이스 등인데, 다행히 모두 위상 정렬 단계에서 잡히는 종류의 문제였다.

검증은 실제 QA 시트로 했다.
실 서비스의 테스트 케이스를 그대로 넣어서, 기존 그룹 기반 실행 결과와 비교했다.
실행 시간이 줄고, blocked 비율도 의미 있게 낮아졌다.

## 교훈

DAG 자체가 정답이라는 생각은 안 한다.
상황에 따라 그룹 기반이 충분히 좋을 수 있다.

다만 의존성이 케이스 개수만큼 늘어나는 상황에선, 실행 순서를 명시적인 그래프로 표현하는 게 장기적으로 더 싸게 먹혔다.
"왜 이 순서인지"를 코드로 설명할 수 있게 되니, 나중에 최적화할 때도 손이 덜 갔다.

그리고 소프트 의존성을 없앤 경험은 계속 남는다.
개발하다 보면 "이러면 더 좋을 것 같은데" 하고 넣게 되는 기능들이 있는데, 그런 것들의 상당수는 실제로는 복잡도만 키운다.

> 복잡함은 개발자 본인을 위한 것이지, 사용자(여기선 QA 결과를 보는 사람)를 위한 게 아니다.
> 이 교훈은 이후 시스템 전반의 설계 기준이 됐다.
