어제 구조를 바꿨으니 오늘은 실제로 돌려보면서 검증하는 날이었다.

agent-browser 스킬이 제대로 동작하는지, fixture knowledge가 정상적으로 조회되는지, 브라우저 격리가 의도대로 동작하는지 하나씩 확인했다.

## 2차 재검증

qa-executor를 실행해서 agent-browser 스킬을 사용하는 전체 흐름을 검증했다.

1차 검증 때는 브라우저 격리가 안 돼서 세션이 꼬였는데, 이번에는 마스터 에이전트만 브라우저를 준비하고 실행 에이전트는 준비된 브라우저만 사용하니까 문제가 없었다.

검증 항목은 이런 것들이었다.

브라우저가 의도한 대로 격리되는지.

실행 에이전트가 마스터가 만든 브라우저 세션을 정상적으로 이어받는지.

테스트 종료 후 브라우저가 깔끔하게 정리되는지.

전부 통과했다.

## thinking 이벤트 로깅

에이전트가 추론하는 과정을 로깅할 수 있게 했다.

LLM이 "thinking" 이벤트를 내보내면 그걸 파일에 기록한다.

에이전트가 실패했을 때 추론 과정을 보면 왜 실패했는지 원인을 파악할 수 있어서 중요하다.

기존에는 결과만 보고 "실패했다"라고만 나오니까 디버깅이 막막했다.

이제는 "이 버튼이 보이지 않아서 대기했다" 같은 추론 과정이 로그에 남으니까 어디서 막혔는지 바로 알 수 있다.

에이전트 프롬프트 5개를 한국어로 번역했다.

영어 프롬프트를 쓰다 보니 가끔 한국어 페이지에서 영어로 응답하는 경우가 있었다.

## executionDraft 도입

플래너가 단계별 실행 초본을 작성할 수 있게 executionDraft 필드를 도입했다.

기존에는 플래너가 실행 계획을 수립하면 바로 실행 에이전트에 전달했다.

계획 단계에서 초안을 한 번 거쳐서 검토할 수 있으니까 계획 품질이 올라갔다.

## fixture knowledge 정상화

fixtures.sqlite에 접근하는 흐름에 문제가 있었다.

executor가 fixture를 조회할 때 경로가 꼬여서 이전 실행에서 저장한 지식을 못 불러오고 있었다.

경로를 수정하고 조회 흐름을 개선했다.

이제 같은 URL에 대한 fixture가 정상적으로 재사용된다.

## delegation 루프

qa-master에 delegation 루프를 도입했다.

기존에는 마스터가 직접 모든 에이전트를 호출하는 구조였다.

이걸 task 기반 실행으로 바꿨다.

마스터가 task를 만들고, 각 에이전트가 task를 받아서 실행하고, 완료하면 다음 task로 넘긴다.

루프 구조니까 중간에 실패한 task를 재시도하거나 순서를 바꾸는 것도 유연해진다.

## 마무리

검증을 통과하고 나니 구조 변경이 제대로 동작한다는 확신이 생겼다.

thinking 이벤트 로깅 덕에 디버깅이 한결 수월해졌다.

delegation 루프도 앞으로 재시도 로직을 붙이기 좋은 기반이 됐다.
