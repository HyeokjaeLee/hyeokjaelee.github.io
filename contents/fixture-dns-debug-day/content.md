두 가지 디버깅이 하루를 채운 날이었다.

하나는 설계 문제, 하나는 인프라 문제.

둘 다 실행 흐름을 깨뜨리는 거라서 긴급하게 잡았다.

## Fixture Knowledge 참조 수정

플래너가 fixture knowledge를 참조하는 흐름에 문제가 있었다.

fixture knowledge는 이전 실행에서 학습한 fixture 데이터를 저장하는 SQLite 저장소다.

플래너가 실행 계획을 수립할 때 이전 지식을 조회해서 재사용한다.

그런데 참조 경로에 문제가 있어서, 플래너가 fixture를 못 불러오고 있었다.

매번 이전 지식 없이 처음부터 학습하니까 실행 시간이 길어지고 비용이 늘었다.

참조 흐름을 수정하고, fixture 조회가 정상적으로 동작하는지 검증했다.

## GLM DNS 해석 실패

갑자기 GLM 모델 호출이 전부 실패하기 시작했다.

에러 로그를 보니 DNS 해석 실패.

GLM API 엔드포인트의 도메인이 해석되지 않는 거다.

DNS 서버 문제인 줄 알고 확인해봤지만, DNS 서버 자체는 정상이었다.

문제는 Docker 컨테이너 내부의 DNS 해석이었다.

컨테이너가 외부 DNS를 제대로 못 찾고 있었다.

proxy URL을 명시적으로 오버라이드해서 해결했다.

> 컨테이너 DNS 문제는 겉보기엔 서버 장애 같지만 실제로는 컨테이너 설정 문제인 경우가 많다.

## ClawMux 요청 파이프라인

ClawMux의 요청 처리 파이프라인을 7단계로 분석했다.

요청이 들어와서 라우팅되기까지 7단계를 거치는데, 각 단계에서 무슨 일이 일어나는지 문서화했다.

ZAI GLM의 `reasoning_content` 폴백 버그도 수정했다.

GLM이 reasoning 응답을 줄 때와 안 줄 때 처리가 달라서, 폴백 로직을 추가했다.

테스트 587개가 전부 통과했다.

## 사이드 프로젝트

괴담 소설 사이드 프로젝트에서 TTS 대사 포맷을 개선하고, 선택지와 투표 기능을 전면 제거했다.

쓸데없는 기능을 빼니까 프로젝트가 단순해졌다.

## 마무리

두 가지 디버깅이 긴급했지만 둘 다 근본 원인을 찾아서 해결했다.

특히 DNS 문제는 겉보기엔 복잡해 보였지만 컨테이너 설정 하나로 끝났다.
