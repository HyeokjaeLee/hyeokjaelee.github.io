플래닝이 멈추는 문제를 해결하면서 스킬 시스템도 정리한 날이었다.

## Planning 멈춤 문제

28개 케이스를 planning할 때 멈추는 현상이 있었다.

케이스 수가 적을 때는 괜찮은데, 20개를 넘어가면 플래너가 응답하지 않고 멈춰버린다.

원인은 컨텍스트 초과였다.

한 번에 28개 케이스를 전부 planning하려니까 컨텍스트 윈도우가 가득 차서 LLM이 응답을 못 내놓는 거다.

## 3-Phase Planning Pipeline

planning을 3단계로 나눴다.

Phase 1에서는 전체 케이스의 골격만 잡는다.

케이스 의존성과 실행 순서만 결정하고, 세부 내용은 넘어간다.

Phase 2에서는 골격을 기준으로 그룹별로 병렬 planning을 돌린다.

그룹마다 별도의 planning 세션이 할당되니까 컨텍스트가 터지지 않는다.

Phase 3에서는 각 그룹의 planning 결과를 하나로 조립한다.

이렇게 나누니까 28개 케이스도 멈추지 않고 planning이 완료된다.

## 스킬 도메인 비종속 정책

스킬에 하드코딩된 도메인 특화 정보가 문제였다.

스킬 안에 특정 서비스의 URL이나 셀렉터가 박혀 있었다.

이걸 플레이스홀더로 치환해서 스킬이 특정 도메인에 종속되지 않도록 했다.

24개 스킬을 21개로 통합했다.

비슷한 역할을 하지만 도메인만 다른 스킬들을 하나로 합쳤다.

이름도 URL 기반에서 행위 기반으로 바꿨다.

"코스_생성_검증" 같은 도메인 종속 이름 대신, "폼_작성_및_제출_검증" 같은 행위 중심 이름으로 변경했다.

## Planner 프롬프트 인라인 전달

플래너에게 파일 경로를 참조하게 하는 대신, 실제 파일 내용을 프롬프트에 직접 포함시켰다.

파일 경로를 참조하면 에이전트가 파일을 읽는 도구를 호출해야 해서 한 단계가 더 생긴다.

내용을 직접 주면 그 단계가 사라진다.

## 마무리

3-Phase Planning으로 케이스가 많아도 planning이 멈추지 않게 됐다.

스킬 도메인 분리로 같은 스킬을 다른 서비스에도 재사용할 수 있게 됐다.
