## 왜 Gemini CLI를 통합했나

요즘 OpenCode를 메인 코딩 에이전트로 쓰고 있다.

OpenCode 자체가 Claude, GPT 같은 상용 모델을 잘 지원하지만, Gemini는 따로 챙겨야 하는 일이 잦았다.

컨텍스트가 길 때, 코드 분석이 필요할 때 Gemini를 한 번 거쳐가면 유리한 케이스가 꽤 있다.

그래서 격리된 Gemini CLI를 OpenCode 서브에이전트처럼 호출하는 통합 시스템을 구축해봤다.

단순히 CLI를 한 번 부르는 수준이 아니라 샌드박스 분리부터 프리셋 시스템, 백그라운드 실행까지 한 덩어리로 만드는 게 목표였다.

## 샌드박스로 완전 분리하기

가장 먼저 신경 쓴 건 OpenCode 설정을 오염시키지 않는 거였다.

`@google/gemini-cli@0.38.2`를 로컬에 설치하고, mjs 기반 bridge 모듈(bridge.mjs, bin.mjs, paths.mjs)로 샌드박스를 만들었다.

Gemini CLI가 참조하는 디렉토리를 통째로 분리해서 OpenCode 쪽 설정이랑 섞이지 않게 했다.

MCP는 OpenCode와 독립적으로 관리한다.

호출 인터페이스는 `gemini_consult`, `gemini_status` 같은 OpenCode 플러그인 툴로 노출했다.

## npm 캐시 오염 버그

여기서 가장 짠났던 부분이 npm 캐시였다.

초기 구현은 `HOME`만 바꿔치기하는 수준이었는데 Gemini CLI가 npm 캐시를 공유 디렉토리에 쓰는 바람에 메인 환경이 꼬였다.

해결책은 단순했다.

`npm_config_cache`를 명시적으로 주입해서 샌드박스 안쪽으로 캐시를 강제하는 거다.

비슷한 이유로 `getStatus()`에서 인증 오류가 났던 것도 paths.mjs에 올바른 경로 상수를 추가해서 잡았다.

Gemini CLI가 `GEMINI_CONFIG_DIR`를 지원하지 않고 `/Users/nagle/.gemini/`를 하드코딩하는 것도 삽질 거리였다.

## 프리셋 시스템

여기까지 하면 "부르기는 부른다" 정도인데, 실제로 쓰려면 용도별 프리셋이 필요하다.

그래서 `agents-gemini/` 디렉토리에 `.md` 파일로 프리셋을 정의하는 구조를 만들었다.

`.md` 파일을 하나 추가하면 OpenCode가 `gemini_<파일명>` 형태의 동적 툴로 자동 등록한다.

플러그인을 재시작할 필요 없이 파일 하나 추가만으로 새 프리셋이 바로 먹힌다.

이게 생각보다 편하다.

코드 수정이나 설정 리로드 없이 프리셋을 쌓을 수 있으니까.

## 백그라운드로 돌리기

서브에이전트가 동기로만 도는 건 실용성이 떨어진다.

긴 작업은 백그라운드로 맡겨두고 OpenCode 쪽에서는 다른 일을 하는 게 자연스럽다.

백그라운드 동작까지 확인하는 데 수정이 4개쯤 더 들어갔다.

`process.execPath`, wrapper의 `err` 처리, `elapsed_ms` 측정, 로케일 설정 정도.

마지막엔 orphan 프로세스가 3개 남아 있어서 그것도 정리했다.

정리하고 나니 백그라운드 서브에이전트가 안정적으로 돈다.

## 모델 선택

처음엔 기본 모델을 `gemini-3-flash-preview`로 잡았다.

쓰다 보니 품질보다는 속도가 필요한 자리가 많아서 `gemini-2.5-flash`로 기본을 바꿨다.

모델마다 용도, 금지 상황, 특성을 정리한 가이드도 같이 붙였다.

동적 프리셋 설명이 자동으로 반영되니까 프리셋별로 어느 모델이 어울리는지 툴 설명만 봐도 알 수 있다.

## 느낀 점

기대보다 공이 많이 들었다.

단순히 CLI를 subprocess로 부르는 거라면 금방 끝날 줄 알았는데 샌드박스 격리와 npm 캐시 관리가 본질이었다.

일단 한 번 틀을 잡아두면 프리셋 추가 비용이 거의 없다는 게 큰 장점이다.

앞으로 다른 외부 도구를 연동할 때도 비슷한 패턴으로 가려 한다.

> 관련 페이지: OpenCode 프로젝트 정리는 위키 쪽에 따로 뒀다.
