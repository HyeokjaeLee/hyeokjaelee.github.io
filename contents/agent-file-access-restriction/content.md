## 파일을 직접 만지던 구조의 문제

기존 QA Agent는 planner, executor, sheet-writer가 각자 필요한 파일을 직접 읽고 훑었다.

직관적이긴 하다.

역할이 나뉘어 있어도 "필요한 걸 그때그때 열어본다"는 건 사람이 일하는 방식과 비슷하니까.

하지만 에이전트가 늘어나면서 꼬이기 시작했다.

같은 디렉토리를 여러 에이전트가 동시에 뒤지고, 어디서 무엇을 읽었는지 추적이 안 됐다.

탐색 로직이 역할마다 미묘하게 달라서, planner가 잡은 파일 경로와 executor가 잡은 경로가 어긋나는 일도 있었다.

한마디로 요약하자면, "읽는 주체가 많을수록 일관성은 깨진다"는 당연한 사실을 확인한 셈이다.

## 탐색을 explore로 몰기

그래서 파일 탐색을 통째로 `explore` 서브에이전트에 위임했다.

planner는 더 이상 파일을 직접 열지 않는다.

executor도 마찬가지다.

sheet-writer도 마찬가지다.

대신 탐색이 필요한 순간에는 explore에게 "이 영역을 뒤져봐라"고 요청하고, 결과만 돌려받는다.

정보의 흐름이 단방향으로 정리됐다.

```
planner → explore → 결과
executor → explore → 결과
sheet-writer → explore → 결과
```

explore만 파일시스템을 만지고, 나머지는 받은 요약으로 일한다.

## 왜 이 구조가 나은가

가장 큰 이득은 일관성이다.

탐색 로직이 한 곳에 모였으니, 경로 해석이나 우선순위 규칙이 바뀌면 explore만 고치면 끝이다.

부수 효과도 있었다.

planner와 executor가 더 이상 파일 입출력에 시간을 쓰지 않으니, 본질 역할인 계획과 실행에 집중하게 됐다.

explore는 탐색만 전담하므로 캐싱이나 인덱스 재사용 같은 최적화도 자연스럽게 들어갈 수 있다.

관심사 분리(Separation of Concerns)를 에이전트 설계에 그대로 옮긴 셈이다.

## 남는 과제

물론 공짜는 아니다.

모든 탐색이 explore를 거치므로 홉(Hop)이 하나 늘었다.

단순한 파일 하나를 읽을 때도 서브에이전트 호출 비용이 든다.

그래서 "이 정도는 그냥 직접 읽게 해줘"라는 유혹이 생기는데, 여기서 경계를 흐리면 다시 원래 구조로 돌아간다.

원칙을 세워뒀다.

파일을 열고 싶으면 무조건 explore로 간다.

예외를 두는 순간 일관성이 무너지는 걸 이미 겪었으니까.

다음에는 explore 내부의 캐싱을 개선해서 홉 비용을 줄여볼 생각이다.
