스모크 테스트 통과율이 50%였다.

절반은 실패하거나 blocked 처리된다는 뜻이다.

이걸 61%까지 끌어올린 날이었다.

## blocked 재시도

케이스가 blocked 되는 이유는 다양하다.

페이지 로딩이 느려서 요소를 못 찾았거나, 일시적인 네트워크 오류거나, 에이전트가 페이지를 잘못 해석했거나.

이런 케이스들을 그냥 실패로 처리하면 억울한 케이스가 많다.

blocked 케이스만 모아서 재시도하는 로직을 넣었다.

재시도할 때는 이전 실패 원인을 컨텍스트에 포함시킨다.

예를 들어 "이전에 로그인 버튼을 못 찾아서 blocked됨"이라는 정보를 주면, 재시도할 때 더 꼼꼼하게 페이지를 탐색한다.

### 그룹 레벨 재시도

단일 케이스 재시도 외에 그룹 단위 재시도도 추가했다.

같은 그룹에 속한 케이스들이 연쇄적으로 실패하면 그룹 전체를 처음부터 다시 실행한다.

한 케이스의 부작용이 후행 케이스에 영향을 줬을 때 전체를 재시도하는 게 효율적이기 때문이다.

## Zod 스키마 도입

실행 계획과 케이스 결과를 Zod 스키마로 사전 검증하기 시작했다.

기존에는 플래너가 내놓은 실행 계획을 그대로 실행에 넘겼다.

계획에 필수 필드가 빠져 있으면 실행 단계에서 에러가 나고 그때서야 문제를 발견할 수 있었다.

Zod 스키마로 실행 계획의 구조를 정의하고, 계획이 수립되는 시점에 검증한다.

필수 필드가 빠지거나 타입이 틀리면 계획 수립 단계에서 실패하고 자동으로 재시도한다.

실행 단계까지 가지 않으니까 낭비되는 실행 시간이 줄었다.

## 뷰포트 프리셋

모바일, 태블릿, 데스크톱 뷰포트 프리셋을 도입했다.

기존에는 데스크톱 화면만 테스트했는데, 실제 사용자 중 모바일 비율이 높으니까 모바일 뷰포트 테스트가 필요했다.

iPhone SE, iPad, 일반 데스크톱 해상도 세 가지 프리셋을 만들었다.

케이스마다 어떤 뷰포트로 테스트할지 지정할 수 있다.

## 업무 프로젝트 작업

같은 날 업무 프로젝트에서 모바일 홍보 페이지 개선과 학습활동 관리 버그 수정을 했다.

QA 에이전트 작업이 주라 여기는 짧게 적는다.

## 마무리

통과율 50%에서 61%로 올리는 데 재시도 로직이 핵심이었다.

Zod 스키마는 앞으로 실행 계획 복잡도가 올라가면 더 빛을 발할 것 같다.
