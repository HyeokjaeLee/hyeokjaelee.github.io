플래너의 의존성 판정 로직을 다시 짠 날이었다.

## 의존성 판정의 어려움

플래너는 각 테스트케이스가 어떤 다른 케이스에 의존하는지 판정한다.

"코스 생성" 케이스가 끝나야 "강의 수강" 케이스를 실행할 수 있다.

이 의존 관계를 플래너가 정확하게 판정해야 DAG가 제대로 동작한다.

기존에는 플래너에게 "이 케이스들 간의 의존성을 분석해"라고 막연하게 물어봤다.

LLM이 판정을 내리긴 하지만 정확도가 들쭉날쭉이었다.

## Q-UI/Q-RUNTIME 두 가지 질문

의존성 판정을 두 가지 구체적인 질문으로 분해했다.

Q-UI: "이전 케이스가 UI 상태를 변경하는가?"

예를 들어 "로그인" 케이스는 로그인 상태를 만드니까 이후 케이스는 로그인된 상태에 의존한다.

Q-RUNTIME: "이전 케이스가 런타임 데이터를 생성하는가?"

예를 들어 "코스 생성" 케이스는 코스 ID를 만드니까 이후 "강의 수정" 케이스는 그 코스 ID에 의존한다.

이 두 질문으로 의존성을 판정하니까 정확도가 올라갔다.

## cascade block 복원

`hardBlockDownstream` 플래그가 의도대로 동작하지 않는 버그가 있었다.

어떤 케이스가 실패하면 하위 의존 케이스를 자동으로 blocked 처리해야 하는데 이 cascade가 안 되고 있었다.

원인은 의존성 판정이 부정확해서 cascade 대상이 제대로 식별되지 않은 거였다.

Q-UI/Q-RUNTIME 모델로 의존성이 정확해지니까 cascade block도 자연스럽게 복원됐다.

## 패스율 73.3%

30개 케이스 중 22개가 통과했다.

73.3%다.

스모크를 시작할 때 50%에서 출발해서 한 달 만에 23% 포인트가 올랐다.

> 패스율이 올라가는 핵심은 의존성 정확도였다. 의존성이 틀리면 cascade가 안 되고 cascade가 안 되면 실패한 케이스의 하위 케이스들이 무의미하게 실행되면서 패스율이 떨어진다.

## 마무리

Q-UI/Q-RUNTIME은 간단한 프레임이지만 효과는 컸다.

LLM에게 막연하게 물어보지 말고 구체적인 질문으로 분해하는 게 중요하다는 걸 다시 느꼈다.
