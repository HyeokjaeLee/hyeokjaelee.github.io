어제 lane 동적 선택과 Slack 메시지 정리를 했으니 오늘은 결과 품질과 실행 비용을 잡는 날이었다.

Slack에 올라가는 결과가 읽기 불편했고, 반복 실행 때마다 매번 전체 계획을 다시 세우는 게 비용 낭비였다.

그리고 LLM 모델 설정이 코드 여기저기에 하드코딩되어 있어서 바꾸기도 어려웠다.

이 세 가지를 하루 안에 잡았다.

## Slack 출력 개선

기존 Slack 결과는 케이스 하나당 스크린샷, 로그, 상세 리포트가 올라왔다.

결과가 한눈에 안 들어온다.

스크린샷에 페이지 URL을 포함시켜서 어느 페이지에서 발생한 결과인지 바로 알 수 있게 했다.

그리고 케이스 제목을 검증 조건 중심으로 바꿨다.

기존에는 "코스 생성 - 케이스 3" 같은 의미 없는 제목이 달렸는데, 이제 "강의 완료율 100% 시 순차 잠금 해제 검증"처럼 뭘 검사했는지 제목만 봐도 알 수 있다.

## 시트 단위 캐싱

같은 시트로 QA를 여러 번 돌리는 경우가 많다.

버그를 고치고 다시 검증하거나, 새 기능이 추가돼서 회귀 테스트를 돌리거나.

그런데 매번 전체 케이스를 처음부터 다시 계획하는 건 낭비다.

시트 단위 캐시 구조를 만들었다.

한 번 실행한 시트는 planning 결과를 캐싱해두고, 다음 실행 때 변경된 케이스만 부분적으로 재계획한다.

변경이 없는 케이스는 이전 실행 결과를 그대로 가져다 쓴다.

실행 시간이 절반 가까이 줄었다.

### 실행 지식 재사용

성공한 케이스에서 얻은 실행 지식을 스킬로 승격하는 수명주기를 정리했다.

예를 들어 "로그인 페이지에서 비밀번호 입력 필드가 렌더링되기까지 2초 대기가 필요하다" 같은 지식을 캐싱해두면, 다음 실행 때 같은 페이지에서 대기 시간을 다시 탐색하지 않아도 된다.

이 지식이 언제 만료되고 언제 승격되는지 기준을 세웠다.

> Fixture Knowledge와는 다른 레이어다. Fixture는 URL 기반 fixture 데이터고, 여기서 말하는 실행 지식은 케이스 실행 중 얻은 탐색 경험이다.

## 모델 preset 분리

LLM 모델 설정이 문제였다.

Planner는 어떤 모델을 쓰고, Executor는 어떤 모델을 쓰고, Inspector는 어떤 모델을 쓸지 각 에이전트마다 다르다.

그런데 이 설정이 런타임에 인라인으로 박혀 있었다.

모델을 바꾸려면 코드를 찾아서 고쳐야 했다.

provider별 preset 모듈로 분리했다.

이제 preset 파일 하나에서 각 에이전트가 어떤 모델을 쓸지 정의한다.

Planner는 추론이 중요하니 비싼 모델을, Executor는 실행 속도가 중요하니 가벼운 모델을 쓰는 식으로 역할에 맞춰 배정한다.

설정을 바꾸면 전체 에이전트에 즉시 반영된다.

## 마무리

캐싱 정책 도입 후 반복 실행 체감이 확 난다.

같은 시트로 두 번째 실행을 돌리면 변경된 케이스만 도니까 끝나는 시간이 확연히 빠르다.

모델 preset도 유지보수가 편해졌다.

더 이상 모델 바꿀 때마다 코드를 뒤지지 않아도 된다.
